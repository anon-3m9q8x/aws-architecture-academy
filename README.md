## Edition 09.3 — 資格問題を本番形式(長文シナリオ・文章の選択肢)に書き直し(作業中)

- 本番試験と CloudTech の問題集に合わせ、問題文を「状況 → 現状・課題 → 制約 → 問い」の長文シナリオに、選択肢を「〜します。」の 2 文程度の具体的な構成案に書き直しています。正解・解説・「なぜ間違いか」・下線部分も新しい選択肢に合わせて作り直し、根拠ラインは新しい問題文から計算し直します。
- 進捗: SAP-C03 の全 250 問と DOP-C02 の 150 問(計 400 問)を書き直し済み。問題文の中央値 168 → 約 313 字、選択肢の中央値 74 → 約 108 字。どの不正解も「実際に使われる設定だが、この問題の制約のどこかに反する」構成にし、正解が最も長い選択肢になる割合は約 29% に抑えています。今後 DOP の残り → 専門知識 → アソシエイト → 基礎の順に進めます。
- 文字数の目安(`tools/rewrite-lib.mjs`): プロフェッショナル(SAP / DOP)問題文 280〜520 字・選択肢 80〜240 字、専門知識 230〜460 字・70〜220 字、アソシエイト 180〜380 字・55〜180 字、基礎 90〜260 字・20〜120 字。
- 書き直しは `data/rewrite/<試験>-<先頭の番号>.json(10 問ずつ)`(`{ 問題id: { q, o, a, e, why } }`)に保存し、`node tools/apply-balance.mjs`(最後に `tools/apply-rewrite.mjs` を自動実行)で問題データと `data/why/index.js` に反映します。`node tools/check-rewrite.mjs` で形式・文字数・下線部分・「正解だけが長い/短い」手掛かりを検証できます。書き直した問題には `data/balance` の文字数調整は当てません。

## Edition 09.2 — 選択肢の文字数で正解が分からないように

- 資格試験の問題(13 資格)で、正解の選択肢だけが長く、文字数で正解が分かってしまう問題を直しました。2,810 問・7,534 個の不正解の選択肢に、もっともらしいけれど誤りの具体的な内容を書き足し、正解と同じくらいの長さにしています。
- 正解が他のどの選択肢より 15% 以上長い問題: 資格ごとに 37〜90% → 0〜4%。正解の長さ ÷ 不正解の平均の長さ(中央値): 1.24〜2.06 → 約 1.0。
- 正解の選択肢・解説・「なぜ間違いか」は変えていません。下線部分(間違いに直結する部分)はすべて本文に残しています。
- 書き足しで新しい手掛かりが生まれないよう、正解にほとんど出てこない書き方(「〜ため、」「〜よう、」、2 文に分ける、「〜して、」のつなぎ、「〜目的で」「〜前提で」などの前置き)は使っていません。
- 用語だけの選択肢(戦略名・柱名・API 名など)は、説明を付け足すと逆に手掛かりになるため対象外です。
- 書き直しは `data/balance/*.json` に保存し、`node tools/apply-balance.mjs` で問題データに反映します(`tools/build-questions.mjs` で作り直したときも自動で反映)。`node tools/check-balance.mjs <パッチ> [作業ファイル]` で長さ・下線部分・書き方を検証できます。

## Edition 07 — コマンド・ポリシー演習(AWS Command & Policy Lab)

設計書「AWS Command & Policy Lab」の Phase 1(MVP)を実装。サイドバーの **⌘ コマンド・ポリシー演習**(`#command-lab`、各問は `#command-lab/<問題ID>`)から使えます。既存の図鑑・構築問題・資格問題演習は変更せず並存します。

- **IAM JSON エディター**: 行番号、整形、補完候補、記号の入力補助、文字サイズ、拡大。JSON の構文エラーは行・列と直し方の手掛かりを表示。IAM の構造チェック(Action / NotAction などの排他、ポリシーの種類ごとの Principal・Resource の要否、S3 の ARN と操作の組み合わせ)と、過剰な許可のセキュリティ警告。

- **API リクエストラボ**(`lab-engine/simulator-api.js`): Method / URL / Headers / Body。API Gateway(ステージ・ルート・Cognito・API キーと使用量プラン・リクエストの検証)、DynamoDB(GetItem / PutItem / Query / DeleteItem、型付きの値、LeadingKeys)、Lambda Invoke、S3 REST。署名は模擬(`Credential=SIMULATED-<名前>`)。

- **学習記録**: `aaa.commandLab.progress.v1`(試行回数・ヒント回数・クリア・復習フラグ・最終実行日時)と `aaa.commandLab.drafts.v1`(下書き)。`schemaVersion` 付きで不正な値は読み飛ばし、アカウント同期とバックアップの対象。本物の認証情報らしい文字列は下書きに保存せず、送信もしません。ホームにクリア数のカードを追加。

## Edition 06.13 — KMS のマルチリージョンキーとクライアントサイド暗号化を強化

- KMS の「マルチリージョンキー」を全面改訂: 同じキーマテリアルと「mrk-」で始まる共通のキー ID、暗号文に埋め込まれたキー ID による相互復号、レプリカは独立したキー(ポリシーはリージョンごと、片方のリージョンだけで暗号化・復号を継続)、プライマリへの依存はローテーションとプライマリの変更のみ。単一リージョンキーはリージョンをまたいで復号できず、マルチリージョンキーへ変換もできない点を注意として強調。
- 「クライアントサイド暗号化(CSE-KMS)と SSE-KMS」を追加: 違いは暗号化の演算をどこで行うか。GenerateDataKey による使い捨てのデータキー、マスターキーは HSM の外に出ない、CRR では暗号化済みのバイト列だけが複製されるため宛先での復号にマルチリージョンキーが必要。SSE-KMS の CRR では S3 がマルチリージョンキーも単一リージョンキーとして扱い再暗号化する点も追記。公式ドキュメント(Multi-Region keys)で照合。
